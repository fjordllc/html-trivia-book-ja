## 優先して修正する技術説明

### 1 引用符が必要になる例に空白がない

対象: `manuscript/part3/chapter11.md:35–42`。

`<a title=会社概要ページ>` に対して「空白を含む時点で」と説明していますが、例に空白はありません。この属性値は引用符なしで記述できます。実際に ASCII スペースを含む `title=会社 概要` と `title="会社 概要"` を対比してください。日本語そのものが引用符を必要とする、という誤解も防げます。[属性の構文](https://html.spec.whatwg.org/multipage/syntax.html#attributes-2)

### 2 正しいタグ省略を壊れた入力として扱っている

対象: `manuscript/part2/chapter6.md:3–56`、`chapter7.md:15–49`。第4・5・8章、図6-1、図14-1、アウトラインにも波及します。

第7章の三例は、適切な本文内に置く断片としては、それぞれ通常の省略規則で説明できます。`p` の直後が `div` なら終了タグを省略でき、例の `li` は `div` を内容に持てて、親の末尾では終了タグを省略できます。`tbody` のタグ省略も、それ自体はエラーではありません。

まず「正しい省略」を示し、そのあとに `<p>前置き<div>本文</div></p>` の余った終了タグなど、実際にエラーになる入力を示す構成が必要です。文書全体としての DOCTYPE や title の不足は、この断片の入れ子の正否とは分けて扱います。[p の省略条件](https://html.spec.whatwg.org/multipage/grouping-content.html#the-p-element)、[タグ省略](https://html.spec.whatwg.org/multipage/syntax.html#optional-tags)

### 3 tbody の挿入を DOM 全体の必須条件にしている

対象: `manuscript/part2/chapter5.md:9–61`、`123–135`、図5-1のキャプション。

「tr は表の第一階層ではない」「DOM では tbody が必要」は広すぎる断定です。table のコンテンツモデルには、条件付きで直下の tr も含まれます。HTML 文字列のパース時に tbody が挿入されることと、DOM API で table の子に tr を追加することを区別してください。

追加すると有効なのは、同じ表を HTML 文字列から作る場合と `createElement`・`append` で作る場合の対比です。`table > tr` が当たるかどうかは、実際の DOM によって決まる、と説明できます。[table のコンテンツモデル](https://html.spec.whatwg.org/multipage/tables.html#the-table-element)

### 4 パーサーが不適合な構造をすべて修正するように読める

対象: `manuscript/part2/chapter4.md:37–41`、`chapter6.md:9–13`、`chapter7.md:9–11`。

コンテンツモデル違反とパースエラーは同一ではありません。たとえば本文の断片 `<ul><div>補足</div></ul>` は著者向け規則には適合しませんが、div は ul の子として残ります。「置けない要素が来れば、ブラウザが正しい場所へ移す」という一般則はありません。

第4章の title が head に入る例も、入力順とパーサーの状態による結果です。「title はどこに書いても head へ移される」と誤読されない限定が必要です。第6章では phrasing content の説明と、p を閉じるトークンの規則を分けてください。[パース規則](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inbody)

### 5 文字参照の説明と URL の例が誤っている

対象: `manuscript/appendix/d.md:45–51`、付録Aの46。

「&amp; と書いてはじめて & が出る」は誤りです。すべての & が文字参照になるわけではありません。また、引用された URL 属性値中の `?a=1&b=2` の `&b` は、その例では文字参照へ変換されません。

安全な表記として &amp; を勧めることと、パーサーが実際に変換する条件を分けてください。本文中の `&copy;`、そのままの `A & B`、属性値中の例を比較すると説明できます。文字参照と URL のパーセントエンコードも別の処理です。[名前付き文字参照の処理](https://html.spec.whatwg.org/multipage/parsing.html#named-character-reference-state)

### 6 template は複製するだけでは画面に現れない

対象: `manuscript/appendix/d.md:97–99`。

「複製したときに、はじめて本物の DOM として動き出す」は不正確です。内容は最初から DocumentFragment 内の DOM ノードで、文書へ挿入する手順が必要です。`content` の取得、複製、挿入の三段階を短い例で示してください。「まだ存在していない」という比喩も避けるべきです。[template の仕様と挿入例](https://html.spec.whatwg.org/multipage/scripting.html#the-template-element)

### 7 PDF との比較が当時の技術選定の史実に見える

対象: `manuscript/part1/chapter3.md:3–19`、`86–90`。第2章末・第1部導入にも同じ前提があります。

PDF と Acrobat の登場は1993年です。1989年の提案や1990年の Web 実装において、PDF と HTML を比較して HTML を選んだかのような叙述は年代が合いません。「現在の読者に分かりやすい形式比較であり、当時の候補比較を再現したものではない」と明示すれば、比較自体は生かせます。[Adobe の PDF 史](https://blog.adobe.com/en/publish/2015/06/18/who-created-pdf)、[W3C の Web 年表](https://www.w3.org/History.html)

### 8 コメントの危険な並びを具体的に示せていない

対象: `manuscript/part3/chapter10.md:17–30`。

提示した `<!-- ここで -- を多用すると? -->` は、現行 HTML では通常のコメントとして扱える例です。現状の説明は `--` 自体が禁止されるように読めます。現行 HTML と XML・歴史的 SGML の制約を分け、コメントを入れ子にしようとして内側の終了記号で終わる例などへ置き換えてください。[現行 HTML のコメント制約](https://html.spec.whatwg.org/multipage/syntax.html#comments)

### 9 ブール属性の例と省略の分類を修正する必要がある

対象: `manuscript/part3/chapter11.md:11–23`。

`<input checked>` は type の既定値が text なので、checked の適用対象ではありません。`<input type="checkbox" checked>` にしてください。[input の適用属性](https://html.spec.whatwg.org/multipage/input.html#text-(type=text)-state-and-search-state-(type=search))

また、属性名だけの構文は、構文上は空文字列の値を与えるものです。ブール属性専用ではありません。構文、各属性が許す値、属性の意味を分けて説明する必要があります。`disabled="false"` は無効化が続くという挙動だけでなく、適合する値ではないことも補ってください。[ブール属性](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#boolean-attributes)

### 10 廃止要素と実装からの削除を混同している

対象: `manuscript/part4/chapter13.md:3–5`、`manuscript/part6/chapter22.md:19`。

font・center・marquee を一括して「消えた」とすると、後方互換性の章と矛盾して見えます。また「どちらも標準には採用されず」は時期・意味の限定が必要です。現行 HTML には obsolete な marquee の実装要件があります。

「著者が新しく使うべきではない」「互換性のため処理が規定されている」「表示効果が実装から削除された」を区別してください。[Obsolete features と marquee](https://html.spec.whatwg.org/multipage/obsolete.html#the-marquee-element-2)

### 11 JSX の結果が必ず View Source に出るように読める

対象: `manuscript/part2/chapter8.md:39`、`manuscript/part1/chapter1.md:70`。

ERB と JSX をまとめて「評価されたあとにサーバーやビルド結果から渡された HTML」とすると、クライアント側レンダリングを説明できません。React がブラウザ上で作る DOM と、サーバーで生成した HTML を分けてください。これは第8章の中心テーマに直接関係します。[React createRoot](https://react.dev/reference/react-dom/client/createRoot)、[React renderToString](https://react.dev/reference/react-dom/server/renderToString)

### 12 strong と em の区別が曖昧

対象: `manuscript/part5/chapter20.md:24`。

strong を「重要性や強い強調」と定義すると em との違いが曖昧です。「重要性・重大性・緊急性」とし、em の強勢との対比を1例入れてください。b は単に視覚的に目立つ語なら何でもよい、という説明にも広げないほうが正確です。[strong](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-strong-element)、[b](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-b-element)

## 読みやすさと本全体の構成

### 同じ結論を繰り返す章を具体例で分ける

第4章と第8章、第15章と第16章、第2章と第21章、第23・25・26章で論点が重なります。再登場そのものは有効ですが、後の章で新たにできる判断が弱い状態です。

特に第16章には、特定のバグ・変更・影響を追う事例がありません。4節とも「直すと既存ページが壊れる」という説明を言い換えています。章を長くする前に、ひとつの具体的な案件で論証する必要があります。第26章も、仕様の変更記録を一件追うなど、総括の先にある行動が欲しい箇所です。

26章中16章が最初の段落を「この章では」で始め、各章にゴール宣言・前章と次章の案内が続きます。末尾にも同じ案内があるため、短い章ほど構成説明の比率が高くなっています。問いやコードから始め、必要な接続だけ残すと読み進めやすくなります。

### 再現できる例へ整える

第1章45行の `hidden = false` は、直前の要素が元から表示されているので、実行しても表示上の変化がありません。hidden を付けた初期状態を用意するか、true にして隠す例へ変えると、分業を観察できます。

第5章の `table > tbody > tr` と `table tr` は選択範囲が違います。後者は thead・tfoot の行や入れ子の表にも届くため、同等の代案として並べず意図の違いを補ってください。

第9章冒頭の「p にも div にも必ずある閉じタグ」は第6章と矛盾します。「終了タグで内容を囲む要素と、終了タグを書いてはいけない要素」の違いへ直すと自然です。

### 強い断定や意図の推測を限定する

- 第2章9行の「誰よりも先に」は、情報共有問題が CERN に固有・最初だったかのように読めます。CERN における具体的な問題へ限定する。
- 第2章91行の「仕様書の大半がパーサー」は量的な根拠が示されていません。「パース規則も詳しく規定する」程度にする。仕様はフォーム、ナビゲーション、スクリプトなども広く扱います。[HTML Standard の構成](https://html.spec.whatwg.org/multipage/introduction.html)
- 第19章9行の div は「どこにでも置ける」わけではありません。「用途を限定しない汎用コンテナ」とし、配置にはコンテンツモデルの制約があると補う。
- 付録D17行の「中身を理解させることをあきらめ」は設計者の意図の推測です。歴史的な描画モードとの互換性という確認可能な理由に置き換える。
- 付録D25行の script は、示した例では終了タグで閉じますが、「最初に現れたら必ず」は script の特殊なパーサー状態まで含めると強すぎます。「この例では」と限定し、一般的な安全なエスケープ方法を仕様の該当節へ案内する。
- 付録Dの「空白は1個」は通常の CSS の空白処理を前提とする、と先に限定する。「1文字分」は全角幅と誤解されるため「半角スペース1個相当」とする。
